# 基础硬件调试协议 V1

状态（2026-11-07）：前半部分记录当前已实现的V1调试报文，覆盖两块STM32及Python工具；ESP32现有UART查询测试复用此封装。当前固件不包含大小符启停、颜色/灯效、Flash保存、阈值写入、电压采样和电机驱动命令。文末“已确认的正式通信要求”记录本次用户确定的后续行为，尚未实现；本次只更新规范，不变更V1报文布局、协议版本或固件。

后续BLE业务与界面草案见[ESP32蓝牙与上位机通信规范草案](PROTOCOL_BLE_DRAFT.md)。最新界面只显示当轮成绩，历史累计暂缓；随机方向按每次开符重新确定，固定方向以面对击打面为准；返回首页不停止。草案中的V2提案不改变下述已实现V1格式。

除C620反馈的原始帧为大端外，本协议所有多字节整数均为小端。CAN均使用11位标准ID、经典数据帧、8字节DLC。CAN1与C620共线，调试ID避开`0x200/0x1FF/0x201～0x208`。

## CAN：每条线上一块叶片

中心依物理端口编号1～5。五片共用完全相同的固件和CAN报文ID；叶片不保存槽位编号，也不需要逐片编译或按编号烧录。接中心CAN3就是3号叶片，换板后仍由该端口确定槽位。UID是芯片固有身份，只用于识别实物、诊断和区分事件来源，不需要人为烧录。报文中的请求seq只标识一次命令，与叶片槽位无关，例如0x2A表示本次请求序号而不是42号叶片。不能在同一物理总线上接多片使用本协议的叶片。

| ID | 方向 | 字节0～7 |
| --- | --- | --- |
| `0x500` | 中心→叶片 | version=1、请求seq、opcode、value、0、0、0、0 |
| `0x501` | 叶片→中心 | version=1、请求seq、opcode、result、status、0、0、0 |
| `0x510` | 叶片→中心 | version=1、status、ADC错误u16、DMA丢块u16、启动秒数u16 |
| `0x512` | 叶片→中心 | version=1、part=0/1、UID的6字节；两片共12字节 |
| `0x513` | 叶片→中心 | 击打seq u8、ring u8、peak u16、样本时刻ms u32 |
| `0x520+ch` | 叶片→中心 | 快照seq u8、state u8、raw u16、baseline u16、delta i16 |
| `0x530+ch` | 叶片→中心 | 快照seq u8、ring u8、peak u16、样本时刻ms u32 |

`ch=0～9`，对应ADC扫描顺序，环号为`6,7,8,9,10,5,4,3,1,2`。UID字节按`UIDw0/UIDw1/UIDw2`的小端存储顺序发送，约每秒两片，中心只接受part0之后300 ms内到达的part1。

`status`低7位是校准状态：0进行中、1READY、2不稳定；bit7表示采样故障。每路`state`：0校准、1空闲、2候选、3等待释放、4锁定。raw/baseline/peak单位均为ADC计数。

命令opcode：2设置压力流，value=0停止/1开启；3重新校准，value必须为0。压力流租约1500 ms，中心对选中叶片每500 ms刷新开启命令，并向其余叶片发送关闭命令。没有观察请求时仍有心跳和击打事件。心跳200 ms，中心1000 ms未收到该片心跳则标离线。

result：0接受、1参数错误、2不可用/离线、3忙、4超时、5未实现。校准ACK表示重新启动采样/校准成功，不能当作基线已经READY。中心以相同CAN seq重试，间隔300 ms，最多3次；叶片对两秒内重复校准命令返回原结果，不再次复位检测器。

一次快照包含20帧。中心必须凑齐同一seq下所有ch的A/B片，所有B片的时间戳必须相同；100 ms超时、seq变化或时间不一致时丢弃未完成快照。叶片每50 ms冻结一次快照，发送未完成则换新一轮；不在发送过程中读取会变化的传感器数组。

当前V1依赖CAN链路层CRC，调试遥测不逐帧重发；击打暂无应用层确认、去重和断线历史回补。ACK与击打共用最多15条待发送队列，满队列会计数并丢弃。压力快照不是高速原始波形录制。正式版已确认改为可靠击打事件与可丢旧快照分开处理，要求见文末；不能把现有V1当成已满足可靠击打验收。

FDCAN采用40 MHz内核时钟、Prescaler=2、Seg1=15、Seg2=4，1 Mbps、80%采样点。MCP2515采用16 MHz振荡器、CNF1=00、CNF2=98、CNF3=01，1 Mbps、75%采样点；其SPI收发、过滤和RXRTR处理依据[Microchip MCP2515数据手册DS20001801K](https://www.microchip.com/content/dam/mchp/documents/APID/ProductDocuments/DataSheets/MCP2515-Family-Data-Sheet-DS20001801K.pdf)。双方位速率一致，采样点不必相同，实际接线时序仍需上板验证。

## UART二进制帧

叶片USART2：115200/8N1。中心USART1：1000000/8N1。无硬件流控，不依赖一次DMA接收/串口read对应一帧。

| 偏移 | 长度 | 字段 |
| --- | --- | --- |
| 0 | 2 | `A5 5A` |
| 2 | 1 | version=1 |
| 3 | 1 | type |
| 4 | 2 | payload长度N，最大192 |
| 6 | 2 | 请求序号seq；异步遥测通常为0 |
| 8 | N | payload |
| 8+N | 2 | CRC16/CCITT-FALSE，小端保存；poly=1021、init=FFFF、无反射、xorout=0；覆盖偏移2起的6+N字节 |

接收器对非法版本/长度/CRC逐字节重同步；字节间隔超过100 ms丢弃残帧。UART使用512字节循环RX DMA及TC圈数记录、8槽TX DMA队列（可排队7帧）；主循环不等待串口发送，溢出有计数。软件调试时避免长时间阻塞主循环。

### 请求与应答

- `type=0x01`：payload固定3字节`[opcode,port,value]`。
- `opcode=1`：查询状态，port/value均为0。
- `opcode=2`：观察压力，value=1开启/0停止。中心port=1～5，直接连接叶片port=0。中心停止可用port=0,value=0。
- `opcode=3`：重新校准，value=0；中心port=1～5，直接连接叶片port=0。
- `type=0x02`：payload为`[opcode,port,result]`，seq对应请求。压力选择ACK表示中心已接受选择，实际数据还取决于叶片在线与流命令到达。
- 未实现命令明确返回5。状态查询返回`0x10`状态包，不再另外发送ACK。

### 遥测格式

**0x10 叶片状态，28字节：** `[role=1,status,can_ready,bus_off]`，随后6个u32：uptime_ms、adc_errors、dma_drops、uart_errors、uart_tx_drops、can_event_drops。

**0x10 中心状态，140字节：** 头20字节为`[role=2,selected_leaf,motor_write_enabled=0,can_ready_mask]`，随后4个u32：uptime_ms、uart_errors、uart_tx_drops、TIM7中断计数。之后5个端口记录，各24字节：`port u8, online u8, status u8, uid_valid u8, age_ms u16, adc_errors u16, dma_drops u16, can_rx_drops u16, uid[12]`。age_ms饱和到65535；在线与控制器ready是不同字段。

**0x11 CAN事件，12字节：** `port u8,id u16,dlc u8,data[8]`。中心转发击打；直接连接的叶片还通过此包报告心跳。port=0为本地叶片。参考上面的CAN表解释data。

**0x12 完整压力快照，106字节：** `port u8,snapshot_seq u8,sample_ms u32`；随后10个传感器记录，各10字节：`ring u8,state u8,raw u16,baseline u16,delta i16,peak u16`。

**0x14 C620只读反馈，14字节：** `motor_id u8,temp_C u8,angle_raw u16,rotor_rpm i16,current_raw i16,age_ms u32,online u8,motor_write_enabled=0 u8`。电流原值未经安培换算；转速是电机转子反馈，不是机关轴转速；角度原值范围通常0～8191。未收到过的电调不产生此包，收到后约500 ms汇报一次，超过1000 ms显示离线。

## 后续接口边界

BLE桥接必须正确处理UART完整帧的长度、校验和请求对应关系，不能假定一个BLE通知装得下一帧。多控制端裁决、正式状态同步、断线后的训练继续等需在正式协议层实现。本版中心串口只有一个请求来源，不实现多人控制路由或观察者租约。已确认由ESP32维护请求映射并把应答返回命令发起端，不要求叶片知道控制端身份；映射容量、会话失效与序号复用细节待定。

叶片和中心均提供`ParameterStorage_Available()=false`及关闭灯输出的接口。后续加入阈值、Flash、电压或正式灯拓扑时，需要新增明确能力/命令和版本处理，不能悄悄改变本版字段含义。


## 已确认的正式通信要求（2026-11-07，待实现）

本节是用户确认的需求约束，不代表上述V1代码已经实现。新增命令、消息ID、字段位宽、队列容量和超时数值须在后续实现前定版，不能直接复用保留字节而改变V1既有含义。

### 1. 基础功能优先与资源隔离

系统首先保证本地击打检测、机关运转和必要故障保护。界面、成绩展示和历史查询的优先级低于这些基础功能。具体RTOS/中断优先级数值尚未确定。

| 层次 | 内容 | 约束 |
| --- | --- | --- |
| 实时基础任务 | 叶片ADC采样与击打检测；中心电机反馈、控制与故障保护 | 必须在规定时限内执行，不等待BLE、上位机或历史记录完成 |
| 基础运行通信 | 叶片有效检测事件、应用确认、心跳/故障、训练状态转换与必要靶面指示 | 与观测/历史流分配独立的有界资源；击打判定属于运行逻辑，不能降为成绩显示任务 |
| 控制与状态同步 | 命令裁决、给发起者的结果、中心状态广播 | 普通请求有频率和处理预算；已接收的停止/保护动作不受显示队列拖延 |
| 可降级输出 | 压力曲线、扩展遥测、成绩展示、历史补取和日志 | 可降频、合并或丢弃过期数据；缺失要明确标记，不能阻塞基础任务 |

- 叶片检测不等待CAN发送完成；中心的实时控制不等待ESP32或任一客户端确认。
- 击打事件被中心接收后，先完成必要的去重与运行判定；向手机转发、更新统计和保存历史异步执行。
- BLE慢端、控制端退出、历史缓存不足、成绩输出失败不能单独成为停转理由。任何降级不能掩盖真实叶片失联、采样故障或电机故障；已确认的叶片失联停轮停转要求保持有效。
- 各队列、重发与每轮处理量必须有上限。历史缓存不充足时允许明确的历史缺口；基础击打队列溢出必须报告运行故障，具体故障处置另行确定，不能静默漏判或无界等待。
- 不在检测和运转期间为成绩、曲线或日志进行同步Flash擦写。Flash参数保存仍是预留功能。

### 2. 统一叶片固件与唯一运行状态

- 继续按物理CAN1～5编号，五块叶片使用同一固件、同一组CAN ID，无须编号烧录。
- 中心STM32统一决定模式、红蓝颜色、回合、激活叶片、有效击打、成功/失败和连续重开倒计时。ESP32转发，界面显示中心确认的状态。
- 模式或颜色切换命令一旦被中心接受，立即结束当前尝试并切换，不等旧轮自然结束。旧轮结果标明“切换中断”，不能作为正常成功或20秒失败。
- “立即”指业务状态的处理时机，不代表电机速度可以瞬间跳变；切换时的电机过渡和灯输出时序须另行确定。
- 同一个切换请求的重发只能产生一次状态变更，不能再次结束或重开一轮。多端冲突、操作死区长度和停止绕过死区策略仍待定。
- 控制端断开不改变已经运行的流程。任一叶片失联仍按已确认需求停止本轮并停转；当前V1只有离线标记，没有实现该运动保护流程。

### 3. 全局压力观察与自动停止

- 所有观察者共享一个“当前观察叶片”；各客户端不能在本版需求下独立选择不同叶片。获准切换观察对象后，所有观察端同步更新端口，旧快照不再显示为新叶片数据。
- 观察者指实际订阅压力数据的连接；仅连接设备或查看训练首页不自动等于订阅压力。
- 各端可进入/退出压力观察。最后一个观察者退出后，停止压力数据流；退出一个端但仍有其他观察者时继续。
- 正常退出应明确取消订阅；进程崩溃、页面后台不再续订、断连等通过有期限的订阅检测，不能只依靠一次“关闭页面”消息。
- ESP32维护各连接的观察订阅，中心只在存在有效观察需求时刷新叶片压力流。ESP32重启或UART链路中断时，中心的上游观察租约也须过期；中心不能永久续约。
- 无观察需求时，中心停止续约并可下发关闭，叶片保留超时关闭作为兜底。新上游租约周期/超时待定；当前V1中心→叶片的500 ms续约、1500 ms过期是已有配置，不代表已确定上游时限。
- 停止压力流只停止快照通信，不停止ADC、击打检测、击打事件、心跳或机关运转。
- 当前V1尚不跟踪观察者退出；用户断开观察端后中心仍续约选中叶片。该差距必须在正式订阅协议中补齐。

### 4. 校准的运行条件

- 正式业务仅允许在击打测试模式且已确认停转后执行校准；不能仅凭“已发停转命令”允许校准。
- 中心负责模式与停止条件检查，再发送给指定叶片；绕过中心的本地调试入口也须明确维护边界，不能成为训练中校准的旁路。
- 区分请求已接受、校准进行中、READY、不稳定、采样失败。接受ACK不是校准完成。
- 当前V1没有模式和停转门禁；已有重新校准命令与该正式要求之间仍有实现工作。停转判据与超时不在本次擅自定值。

### 5. 中心接收时刻与切换边界

- 正式命中时间窗以中心首次接收到完整、有效的该击打事件的时刻为准，使用中心单调时钟；不得使用手机收到消息的时刻。
- 叶片采样时间保留作诊断，不直接跨板比较，也不作为本版正式判定的回溯依据。该选择意味着通信延迟会计入时间窗，需控制并实测基础事件延迟。
- 为同一事件保存首次接收时间和首次判定结果；重发或历史补取不能刷新其判定时刻或再次驱动状态机。
- 切换模式/颜色后，旧轮已判定事件不能进入新轮。旧轮事件迟到且首次到达的归属也必须解决，不能只按到达时刻自动归入新轮；回合上下文字段与切换握手机制待细化。

### 6. 可靠击打与可丢弃快照

- 压力快照保留最新数据，允许丢弃旧快照，不要求逐帧补发观测历史。
- 击打事件增加启动标识、事件编号、应用层确认与有限重发；同一事件重发保持同一身份和内容。
- 事件身份须能区分叶片更换、重启及编号回绕。建议按“芯片UID/来源身份＋启动代次＋事件序号”识别，字段位宽、启动标识生成与承载方式待定；不得只用环数、峰值或8位序号判断重复。
- 中心对同一事件只执行一次命中判定和状态推进，重复到达时可返回确认/已保存结果。叶片重发不等于新的击打。
- 叶片事件的确认以中心已接收并建立可靠处理状态为边界，不等待手机、成绩存储或历史消费者。ACK究竟表示已可靠入队还是已完成判定，须在实现时给出单一明确语义。
- 中心提供有界RAM缓存，供控制端短期断线重连后补取；历史重放只修复显示/记录，不再驱动实时机关逻辑。超出缓存范围明确告知缺失，不承诺断电或无限离线期间的数据保留。
- 最新范围：Windows与微信本版只显示当轮成绩，暂不实现历史累计；有界短期补取保留，用于当前显示恢复。长期历史及其独立存储方式留待以后，不建立跨平台历史同步。
- 确认、重发和去重必须有固定资源预算；重发次数/间隔、缓存条数/寿命、事件编号长度等待定，后续依据内存和最坏延迟测试选择。

重复事件示例：中心已处理但ACK丢失导致叶片重发；转发链路重试；客户端重连补取时又收到已经展示过的事件。它们是同一件击打事实的多次递送。已确认：两个真实击打产生的独立检测事件即使同环、同峰值，也不能仅据此合并；一次物理击打因振铃误产生多个检测事件，必须在检测层通过去抖/分组解决，不能用通信序号去重代替。

### 7. 应答发给命令发起者（ESP32映射方案已确认，待实现）

命令执行结果应直接返回发起该命令的连接；所有订阅端另行接收中心确认后的统一状态。应答通常说明对应请求、目标、接受/拒绝/完成状态及原因。不要把BLE写入成功当成中心已经执行成功。

问题不在于是否能直回发起者，而在于ESP32合并多个连接到一条UART后，必须保留来源对应关系。例如A和B都发本地seq=1，ESP32若原样转发，中心只回seq=1就不足以选出接收者。

已确认采用ESP32请求映射：ESP32给每个在途请求分配不同的UART序号，保存“UART序号→连接会话、客户端原序号”的映射。中心原样回UART序号，ESP32据表只回发起端；状态变化再广播。叶片不处理多控制端身份。该方案已采纳但尚未实现，本次不改变V1帧字段。

请求重试保持同一映射；需考虑在途数量上限、超时、序号复用、断连后连接句柄复用和ESP32重启。是否增加显式网关会话字段、预期状态版本及具体应答结构，留待正式编码前确定。多端实现不得把复杂路由放进叶片ADC或中心电机控制路径。

### 8. 稳定性验收与待定参数

以下是后续验收要求，本次未执行硬件测试：

- 无上位机、慢客户端、多端频繁请求、20 Hz压力观察和历史补取并存时，采样/检测与电机控制仍满足其时序指标；监测ADC丢块、队列峰值、事件延迟和控制周期抖动。
- 最后观察者退出或异常消失后数据流最终关闭，其他观察者仍在时不误关；关闭观测不改变训练。
- 人为丢失事件或ACK、重复转发、断线重连后不重复判定；两次真实独立事件不被错误合并。
- 模式切换边界、叶片重启、更换和旧事件迟到不会串轮；请求结果回到正确的连接会话。
- 训练中校准被拒绝，停转的测试模式校准流程与READY反馈正确。
- 基础通信故障与显示故障分开处理；任一叶片失联停轮停转，纯控制端断开继续流程。

尚未定值：观察续租/过期时间、可靠事件重发与缓存预算、命令路由表容量及超时、控制死区、停转判据/斜坡、控制周期和允许抖动、最大事件时延、BLE并发数及带宽。稳定可靠是设计与实测验收要求，已有CAN/UART基础收发通过不等于整机可靠性已经验收。
